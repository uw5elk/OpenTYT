# CPS-протокол прошивки (USB CDC) — карта для наступних кіл

Джерело правди — `MDUV380_firmware/application/source/usb/usb_com.c` (`cpsHandleReadCommand`, `cpsHandleWriteCommand`, `cpsHandleCommand`). Цей файл — карта, не специфікація: усе, що в таблицях позначено «не перевірено», виведене з коду, а не з заліза.

Рація в звичайному режимі — USB CDC, `VID:PID 1fc9:0094`, порт `115200` (швидкість CDC неістотна). Кожен запит — один пакет, кожна відповідь — один пакет.

## Формати запитів

| Запит | Байти | Відповідь |
|---|---|---|
| **R** — читання | `'R'`, `area`, `addr[4]` (BE), `len[2]` (BE) | `'R'`, `len[2]`, дані — або один байт `'-'` (відмова). Ліміт довжини — `COM_REQUESTBUFFER_SIZE − 3` = 1533 Б; ми читаємо по 1024 |
| **X** — запис | `'X'`, `підкоманда`, … (див. нижче) | `'X'`, `підкоманда` — або `'-'` |
| **W** — «фіктивний запис» | `'W'`, `x` | `'W'`, `x` (відповідь без дії; потрібна оригінальному CPS) |
| **C** — команди | `'C'`, `команда`, … | `'-'` (загальна) або власна відповідь команди |

Довжину даних треба брати із заголовка **відповіді**, а не з запиту: для `CPS_ACCESS_RADIO_INFO` прошивка підставляє свій розмір (`length = sizeof(radioInfo)`).

## Області читання `CPS_ACCESS_*` (запит `R`)

| № | Назва | Що віддає | Запис | Використовуємо |
|---|---|---|---|---|
| 1 | `CPS_ACCESS_FLASH` | Сирий SPI-флеш за абсолютною адресою (`SPI_Flash_read`). Кодплуг: `FLASH_ADDRESS_OFFSET (0x20000)` + адреса з `codeplug.c`. Винятки: `0x10000..0x10200` — локальна копія калібрування (не сам флеш); якщо читання накриває VFO-канали (`CODEPLUG_ADDR_VFO_A_CHANNEL`), прошивка підміняє їх живими | `X` 1→2→3, сектор 4096 Б | так: `aes_key_store.py`, `custom_data.py`, `stock_key_table.py`, **R24 бекап** (флеш-частина) |
| 2 | `CPS_ACCESS_EEPROM` | Емульований EEPROM = **той самий SPI-флеш від адреси 0** (`MDUV380_EMULATED_EEPROM_ADDRESS_OFFSET = 0`) | **`X` 4 на MDUV380 нічого не робить** (`ok = true` без запису): за кодом, EEPROM можна писати лише флеш-шляхом `X` 1→2→3 (сектори 0…31) | **R24 бекап** (0…0x20000) |
| 5 | `CPS_ACCESS_MCU_ROM` | Довільна пам'ять МК за адресою `address + 0x08000000` (флеш МК і RAM) | — | так: `fwsym.py`, `scandetect.py`, `sweepmode.py` (читання змінних із RAM) |
| 6 | `CPS_ACCESS_DISPLAY_BUFFER` | Екранний буфер `displayGetPrimaryScreenBuffer()`: 160×128×2 Б = **40960 Б**, рядок за рядком | — | так: **R24 знімок екрана**; `amlisten.py` (використовує буфер як канал даних) |
| 7 | `CPS_ACCESS_WAV_BUFFER` | `audioAndHotspotDataBuffer.rawBuffer[address]` (сирий аудіобуфер) | `X` 7 | ні |
| 8 | `CPS_COMPRESS_AND_ACCESS_AMBE_BUFFER` | Стискає аудіобуфер у AMBE (кодек), віддає 32 Б | — | ні |
| 9 | `CPS_ACCESS_RADIO_INFO` | `structVersion u32`, `radioType u32`, `gitRevision[16]`, `buildDateTime[16]`, `flashId u32`, `features u16` (46 Б, LE); `radioType` MDUV380 = **6** | — | так: **R24** (маніфест бекапу, перевірка типу рації) |
| 10 | `CPS_ACCESS_FLASH_SECURITY_REGISTERS` | Регістри безпеки SPI-флеша (`SPI_Flash_readSecurityRegisters`); не на MK22 | — | ні (прошивка читає з них тип дисплея: `0x301D`) |

## Запис `X`

| Підкоманда | Дія |
|---|---|
| `1` | Підготувати сектор: `[2..4]` = номер сектора (BE, 24 біти); прошивка читає його в RAM-буфер. Сектор `0x10000/4096` — локальне калібрування |
| `2` | Надіслати дані: `[2..5]` адреса, `[6..7]` довжина, далі дані (≤ 1528 Б) — лише в буфер сектора |
| `3` | Зафіксувати: стерти сектор і записати 16 сторінок по 256 Б |
| `4` | EEPROM: на MDUV380 — порожня дія (див. вище) |
| `7` (`CPS_ACCESS_WAV_BUFFER`) | Запис у сирий аудіобуфер |

Особливості, важливі для **майбутнього відновлення з бекапу**: запис іде секторами, `flash_write_block()` з `aes_key_store.py` готує рівно ОДИН сектор (запис через межу 4 КБ треба розбивати — це робить `custom_data.flash_write_span`); перед записом у ділянку квіккеїв (`CODEPLUG_ADDR_QUICKKEYS`) прошивка зберігає наявні квіккеї; запис каналів/зон/LUCZ виставляє прапорці, після яких `C 6 0` скидає поточну зону. Жодного запису в R24 немає.

## Команди `C`

| № | Дія |
|---|---|
| `0` | Показати на рації екран CPS (`UI_CPS`). **Для знімка екрана не викликати** — на знімку буде екран CPS |
| `1`, `2`, `3`, `4` | Очистити екран CPS / надрукувати рядок / відмалювати / увімкнути підсвітку |
| `5` | Закрити екран CPS (після запису ID-бази перезавантажує кеш) |
| `6` | Післязаписова обробка (скинути зону після перезапису каналів тощо) |
| `7` | Відновити режим GPS |
| `254` | PING |
| `0x80`, `0x81`, `0x86`, `0x82`, `0x83` | AES: записати ключ, вибрати TX-ключ, завантажити ключ лише в RAM, ключ/прапор каналу |
| `0x84`, `0x85`, `0x88`, `0x89`, `0x92`, `0x93`, `0x94`, `0x95`, `0x97`, `0x98`, `0x99`, `0x9A`, `0x9B`, `0xB2`, `0xB3` | Діагностика AES/SMS/RCTL: кільця подій, захоплення бурстів, лічильники, дамп PDU (частина — лише з відповідними `ENABLE_*`) |
| `0x90`, `0x9C`, `0x9D`, `0x9E`, `0x9F` | Перехід у DFU без кнопок / запис слова внутрішнього флеша (`0x9C` має ще й роль RCTL-конфігу) |
| `0x91` | Поставити в чергу й передати DMR-дані (SMS) |
| `0x96`, `0xA7` | DEV: ін'єкція клавіші / UI-функції |
| `0xA0…0xB1`, `0xB4`, `0xB5` | DEV: спектр, свіпи, регістри AT1846S, AM-огинаюча, проба I2S |
| `0x8A`, `0x8B` | Діагностика дисплея HX8353E |

## Карта SPI-флеша (сирі адреси; перевірено за константами коду)

| Діапазон | Що там | Звідки |
|---|---|---|
| `0x00000…0x20000` | Емульований EEPROM: настройки, канали банку 0, зони, DMR ID (`0xE8`), позивний (`0xE0`), VFO (`0x7590`), квіккеї, APRS-конфіги (`0x1588`) тощо | `codeplug.c` |
| `0x10000…0x10200` | Калібрування (читання області 1 віддає локальну копію) | `usb_com.c` |
| `0x20000…0x30000` | «Custom data» OpenGD77: заставка, звуки, теми, AES-селектор, SMS, RCTL, APRS-режим… (блоки `[тип][довжина]` від зміщення 12) | `custom_data.py`, `CodeplugCustomDataType_t` |
| `0x50000…` | База DMR ID №1 (`DMRID_MEMORY_LOCATION_1 = 0x30000 + FLASH_ADDRESS_OFFSET`) | `uiUtilities.c` |
| `0x9B1B0…0x9B1C0` і далі | Флеш-кодплуг: банки каналів 1…7 (7184 Б кожен: маска 16 Б + 128×56 Б) → контакти (1024×24 Б, з `0xA7620`) → довжини RX-груп (`0xAD620`) → RX-групи (76×80 Б, з `0xAD6A0`, кінець `0xAEE60`) | `codeplug.c`; **R24 бекап: `0x9B000…0xAF000`** |
| `0xAF400…` | Голосові підказки (`VOICE_PROMPTS_FLASH_HEADER_ADDRESS = 0x8F400 + FLASH_ADDRESS_OFFSET`) — одразу за межею бекапу | `voicePrompts.c` |
| `0xD8000…` | Початок бази DMR ID №2 (`DMRID_MEMORY_LOCATION_2 = 0xB8000 + FLASH_ADDRESS_OFFSET`). Як вона співіснує з таблицею ключів нижче (`0xD9F9C` лежить далі за `0xD8000`) — не з'ясовано | `uiUtilities.c` |
| `0xD9F9C + 0x64·keyId` | Стокова таблиця AES-ключів (100 Б на запис; keyId 1…15) — **у бекап не входить** | `stock_key_table.py` |
| `0x100000` | Старий заголовок голосових підказок (`VOICE_PROMPTS_FLASH_OLD_HEADER_ADDRESS = 0xE0000 + FLASH_ADDRESS_OFFSET`) | `voicePrompts.c` |

Спостереження (не перевірено на залізі): `X 1` позначає «запис бази ID» при секторі з адресою `0x30000`, хоча на MDUV380 база №1 лежить за `0x50000` — схоже на успадковане від GD77, де зсуву `FLASH_ADDRESS_OFFSET` немає.

## Що брати для наступних кіл

* **Мелодія / заставка / теми** — блоки custom-data (`0x20000…0x30000`, області 1 + `X`), уже є безпечний читач/писар `custom_data.py`.
* **Голосові підказки та бази ID** — запис великих діапазонів флеша секторами (`X` 1→2→3), як у CPS; потрібен прогрес-індикатор і перевірка після запису.
* **Відновлення кодплуга** — зворотна дія до R24: зіставити `manifest.json` (межі, `radioType`, прошивка) із поточною рацією, писати лише сектори, що відрізняються, і після запису — `C 6` та перечитування й звірка SHA-256.
* **Знімок екрана з клавіатури** разом із ін'єкцією клавіш `C 0x96` дають автоматичні сценарії перевірки меню (як `sweepmode.py`).

## R24: формат екранного буфера (виведено з коду, на залізі не перевірено — крок BK1)

`HX8353E_display.c` зберігає кольори як `PLATFORM_COLOUR_FORMAT_SWAP_BYTES(RGB888_TO_PLATFORM_COLOUR_FORMAT(x))`, тобто `uint16_t` зі зміненим порядком байтів; на little-endian STM32 у пам'яті (і у відповіді рації) **першим іде старший байт звичайного RGB565**, тож піксель читається як `>H`. Для MDUV380 `applicationMain.c` завжди додає `DIPLAYLCD_TYPE_RGB`, отже канали — RGB (R у старших 5 бітах). `tools/cps_link.py` так і декодує; діагностичний режим знімка зберігає ще й варіант `little` та сирий буфер — на випадок, якщо залізо покаже інше.
